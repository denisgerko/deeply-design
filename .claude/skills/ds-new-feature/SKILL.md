# Новая фича по ТЗ

Правила — `CLAUDE.md`, реестр — `figma.config.json`, статус — `STATUS.md`, эталоны — `RECIPES.md`.

## 1. Разбор ТЗ

0. Разложить ТЗ по полям `templates/feature-brief.md` (если пришёл заполненный бриф — взять его).
1. Выписать:
   - экраны и их **тип**: полноэкранный, bottom sheet, page sheet, модалка, меню, тост;
   - **все состояния**: пусто, выбрано, лимит, ошибка, загрузка, с клавиатурой, скролл, успех;
   - переходы, вход и выход из флоу (куда ведут кнопки, что делает Close / Skip);
   - что переиспользуем из продукта и что рисуем новое;
   - переменные из CMS (число опций, длина текстов) — макет должен держать минимум и максимум.
2. Скриншоты-референсы: снять геометрию числами (кроп и увеличение в scratchpad). Масштаб = ширина экрана / ширина кадра.
3. Референс не из Figma продукта → parity условная: ДС продукта и платформа важнее пикселей скриншота. Отличия записать.
4. Спрашивать до начала **только** то, что меняет структуру (тип экрана, вход/выход, single vs multi).
   Остальное — дефолт + вопрос в отчёт.
5. Предложения нативных замен видимых элементов — списком «было → станет», без «да» не применять.

## 2. Таблица соответствия

Для каждого экрана — тип в `RECIPES.md` и эталон для **клонирования** (не собирать бары с нуля).
Для каждого элемента — из чего собираем, по порядку:
1. готовый компонент ДС (`figma.config.json` → `components`, «задача → компонент» в `RECIPES.md`);
2. вариант существующего компонента (новое состояние / размер) — `ds-component`;
3. системный кит платформы — если так делает продукт (`kit/platforms/<platform>.md`, `nativeKit`), через обёртку
   на токенах продукта;
4. новый компонент — `ds-component`, только если элемент повторяется или его нет; причина — в `decisions`.

Новые компоненты делаются **до** сборки экранов, с превью light/dark. Нужен экран продукта как фон, а его нет
в рабочем файле — `ds-reference-screen`.

## 3. Сборка

- **Страница:** `<Фича>` после последней страницы экранов. Светлая секция `<Фича>`, тёмная под ней `<Фича> (Dark)`
  (если dark есть в продукте).
  Крупная фича — несколько секций (основной флоу, состояния полей, ошибки), раскладка слева направо по флоу.
- **Экраны:** размер — `profile.screen`, фон — `T.fill(frame, T.C('screenBg'))` (или как на эталоне), clip.
  Имена `<Экран> (<Состояние>)`.
- **Каркас** — клон эталона из `RECIPES.md`: системные бары, навигация, клавиатура уже с правильными оверрайдами.
- **Прокручиваемый контент** — один auto-layout фрейм `Content`. Прокрученное состояние = отрицательный `y`.
- **CTA** — компонент главной кнопки из `RECIPES.md`, у низа; с клавиатурой — над ней.
- **Ввод текста** → по правилам платформы (`kit/platforms/<platform>.md`): на мобильных — клавиатура по типу поля,
  поле Focused, список доскроллен до поля. Поля без ввода (дата, выбор) — пикер/меню, как в продукте.
- **Тексты** — черновые, правдоподобные (не lorem), на языке продукта. В заметке Start пометить «тексты черновые».
- **Скрипты сборки** — свои, через `kit/run.py` (файл в scratchpad): токены только через `T` (`T.fill`, `T.mkText`,
  `T.pad/gap/radius`, `T.frame`), в начале `await T.fonts()`, в конце вернуть `T.report()` — сырые значения
  и не найденные токены разобрать до отчёта.

## 4. Флоу

`ds-flow-arrows`: слева заметка `Flow Start` (триггер входа + общие правила), справа `Flow End — <Куда>`
для выхода на экраны вне файла. Подписи переходов короткие (`Tap`, `Next`, `Submit`, `Skip`).
Ветки — через BOTTOM-магниты. Стрелки за экранами.

## 5. Dark, констрейнты, проверка

1. Dark (если есть в продукте) — `ds-reference-screen/dark-clone SECTION_ID=…` (клон секции, стрелки ремапятся).
   После клонирования — `ds-verify/touch-render` по тёмной секции, если заголовки/тексты отрисовались устаревшими.
2. `ds-constraints`: dry run → применить к своим экранам; новые роли — в скрипт и таблицу.
3. `ds-verify` целиком: token-audit по обеим секциям и новым компонентам, скриншоты light + dark (крупно 2–3 экрана),
   resize-test, пустые тексты, тёмная тема на всех экранах; `glass-check` — если в ДС есть материалы.

## 6. Регистрация и отчёт

- `figma.config.json`: `work.pages`, `components` (новые/изменённые — с датой в `props`), `screens`, `flows.<Фича>`,
  `decisions.<фича>` (рецепт, отличия, решения пользователя, сделанное сверх ТЗ).
- `STATUS.md`: строка фичи, вопросы, отклонения. `CLAUDE.md`: страница в списке.
- `RECIPES.md`: новый тип экрана — строка с эталоном; новый компонент — строка в «задача → компонент».
- Отчёт: экраны и состояния, что добавлено в ДС, что проверено, отличия от референса, вопросы (отдельно — сверх ТЗ).
  Предложить `ds-handoff`.
