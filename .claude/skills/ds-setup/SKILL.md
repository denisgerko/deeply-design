# Разбор ДС продукта и профиль

Кит ничего не знает о продукте заранее. Цель — за один проход понять, **как устроена именно эта ДС**, и записать
это в `figma.config.json` → `profile` (поля — `kit/PROFILE.md`), чтобы все скрипты и следующие сессии работали
с ней без повторного разбора. Продукт только читаем. Скрипты — через `python3 -I kit/run.py …` (см. `CLAUDE.md`).

## 0. Входные данные

От пользователя: ссылка на файл продукта, ссылка на рабочий файл, платформа. Желательно — файл библиотеки ДС
(если она отдельно) и 4–6 эталонных экранов. Чего нет — найти самому и показать на подтверждение.

Проверить доступ: `get_metadata` без nodeId по каждому файлу. Нет записи в рабочий файл — сказать сразу.

## 1. Профиль: как устроена ДС (read-only)

1. `ds-setup/profile-detect` на файле продукта (на больших файлах — `PAGE_FILTER` со страницами экранов).
   Если ДС в отдельном файле-библиотеке — ещё раз на нём.
2. По результату решить и записать в `profile`:

| Что смотреть в выводе | Решение → поле профиля |
|---|---|
| `colorSources` (variable / style / raw на экранах) | `color.system`: `variables` · `styles` · `raw` |
| `collections` с COLOR | `color.collections` (семантическая коллекция первой, примитивы после) |
| `darkVariableCandidates` / `styleSwapCandidates` | `dark`: `variable-modes` + `collections` · `style-swap` + `styleMap` · `both` · `none` |
| `spacingMap`, `radiusMap` | `spacing.map`, `radius.map` (+ `full`, если есть «пилюля») |
| `fonts` | `fonts` (все начертания из text styles и экранов) |
| `screenSizes` | `screen.sizes` |
| `textStyles`, `colorVariableSample` / `paintStyles` | роли `colors` (screenBg, surface, border, textPrimary, textSecondary, accent, onAccent, icon, iconAccent, danger, dimming) и `text` (title, headline, body, caption, button) — по смыслу имён и по эталонным экранам (`ds-reference-screen/product-dump` покажет, что реально стоит на фоне, тексте, кнопке) |
| `effectStyles` | `effects` (card, sheet, …) |
| `topLevelLayerNames` | `roles`: если бары/шиты/контент названы не по-английски или нестандартно — регулярки для них |
| `remoteComponents` | что из системного кита → `skipInside` и `nativeKit`; что из библиотеки ДС → режим B |
| `materialCandidates` | `materials` (или `null`) |

3. **Сомнительное — не угадывать.** Две похожие коллекции, нет явного dark, цвета на экранах сырые при наличии
   токенов — показать пользователю варианты.
4. **Токенов нет** (`raw` преобладает): не заводить свои молча. Предложить (а) палитру из реально используемых цветов
   (`topRawColors`) или (б) работать с сырыми значениями (`color.system = raw`, всё в `decisions.rawValues`). Спросить.

## 2. Вариант рабочего файла

| Ситуация | Вариант |
|----------|---------|
| ДС локальная в файле продукта | **A** — дубликат продукта (Duplicate делает пользователь). Фичи на новых страницах |
| ДС опубликована библиотекой | **B** — новый файл с подключённой библиотекой. `profile-detect EXPORT_KEYS=true KEY_PREFIXES='[…]'` на файле библиотеки → `profile.keys` (только нужные префиксы). Компоненты библиотеки не редактируем |
| ДС запущена (нет токенов, всё «раздето») | **C** — чистая ДС с нуля. Долго; согласовать до старта |

## 3. Компоненты и эталоны

1. `ds-setup/inventory` (на продукте; `COUNT_USAGE=false` на больших файлах): компоненты по страницам, свойства,
   использование. Главные — кнопки, поля, карточки, строки, бары, шиты, модалки, тосты, затемнение →
   `components` (`id`, `key`, `page`, `props`, `usage`).
2. `ds-setup/screens-scan SIZE='[w,h]'`: экраны и их состав по ролям, плюс `unknownLayerNames` — слои без роли.
   Частые бары/шиты среди них → дописать в `profile.roles` и перезапустить (ролей нет — констрейнты и сканы слепые).
3. По одному эталону на тип экрана из `RECIPES.md` (корень вкладки, список, шторка, шторка с вводом, модалка,
   форма с клавиатурой, загрузка/ошибка). Скриншоты 3–4 ключевых — посмотреть глазами.
4. Системные элементы: берёт продукт их из кита платформы или рисует сам — записать (`nativeKit`); правила —
   `kit/platforms/<platform>.md`.

## 4. Подготовка рабочего файла

- Страница-разделитель (`profile.pages.divider`, по умолчанию `---`) перед страницами экранов; страницы компонентов — до неё
  (`profile.pages.components`).
- Шаблон коннектора: пользователь вставляет вручную (README) → `profile.flow.connectorTemplate`. Без него стрелок нет.
- `profile.flow` / `profile.flow.note` — цвета и стили стрелок и заметок (по умолчанию берутся роли `colors`/`text`).
- `profile.icons` — страница иконок, размер сетки, цвет.

## 5. Проверка профиля (обязательно)

- `ds-verify/preview` с 2–3 главными компонентами → скриншот: light и dark выглядят как продукт → удалить (`CLEANUP=true`).
  Так проверяется, что `dark` и `colors.screenBg` выбраны верно.
- `ds-verify/token-audit` на 1–2 эталонных экранах **продукта** (read-only): почти чисто = профиль понимает ДС.
  Много «не на токене» — значит не тот `color.system` / не те коллекции, или продукт сам на сырых значениях
  (тогда это норма продукта — записать).
- `ds-constraints/constraints` dry run на эталонах (`SECTION_IDS`): мало `noRole`.

## 6. Заполнить файлы

- `figma.config.json` — `product`, `work`, `profile`, `nativeKit`, `components`, `icons`, `images`.
- `CLAUDE.md` — `{{…}}`: продукт, ключи файлов, вариант, платформа, `{{DS_SUMMARY}}` (5–8 строк человеческим языком:
  как заданы цвета, dark, шрифт, шкалы, основные компоненты, особенности).
- `RECIPES.md` — эталоны по типам и «задача → компонент».
- `STATUS.md` — дата, фундамент, открытые вопросы.
- `grep -rn "{{" CLAUDE.md RECIPES.md STATUS.md figma.config.json` — пусто.

## 7. Отчёт пользователю

Коротко: вариант рабочего файла; как устроена ДС (цвета, dark, шрифт, шкалы, сколько компонентов, основные);
эталоны (ссылки); проблемы ДС (нет токенов, дубли, экраны на сырых значениях, нет dark); вопросы, меняющие структуру.
Дальше — первая фича (`ds-new-feature`).
